## Short version (social / Discussions)

**go-health v0.5.0 is out** — a Kubernetes health-probe SDK for samber/do v2
with the three-probe pattern (liveness / readiness / startup), criticality
classification, background caching, and aggregate + federation sub-packages
that merge N probes (in-process or remote) into one health surface.

v0.5.0 adds three things:

1. **`health/checks`** — batteries-included, zero-dependency check functions:
   `Disk(path, minFreeBytes)`, `Memory(maxAllocBytes)`, `HTTP(url, timeout)`,
   `Database(db, pingTimeout)`. Warn-by-default (criticality stays with the
   caller); thresholds are arguments, not constants.
2. **Boot-time critical-name validation** — a typo'd name in
   `WithCriticalServices` now fails `Start()` with `ErrUnknownCriticalService`
   instead of silently blocking the startup latch and downgrading fail to
   warn. **This changes when your binary boots: invalid configuration aborts
   instead of degrading.** Fix is always a name correction.
3. **`health.VersionHandler(stamp)`** — a `{"version":"..."}` build-stamp
   endpoint helper; identity, not health (never checks, never 503, GET-only).

## Longer version (GitHub Discussions / blog)

- **`health/checks` batteries** — each constructor is a
  `func(ctx) error` composing with `NewChecks`, `NewWithHealthCheck`, or any
  recorder. `Disk` stats the filesystem, `Memory` samples
  `runtime.MemStats`, `HTTP` pings a URL, `Database` pings a
  `*sql.DB` (driver-agnostic; the test suite carries an in-process fake
  driver, so the package stays at zero dependencies). Resource checks are
  warn-by-default: an 85% disk threshold is policy, and policy belongs to the
  caller — the 2026-09 fleet review (CV 85%/97.3%, fir 1 GB) proved no
  constant fits everyone.
- **Critical-name validation at Start** — the failure mode this closes: a
  critical service name that never appears in a health-check batch used to
  block the startup latch forever *and* downgrade real failures from 503 to
  warn-degraded (the DiscordSync 2026-08-16 bug class, previously caught only
  by a repo-private guard test). Validation reads the first evaluation batch,
  so it applies uniformly to the injector, recorder, and standalone
  constructor paths — including probes built over an empty injector with a
  recorder. Decision + fleet compatibility scan:
  docs/start-validation-design.md.
- **`VersionHandler`** — wire it yourself next to the probe routes
  (`mux.HandleFunc("/version", health.VersionHandler(stamp))`). The payload
  is pre-marshaled at construction; per-request cost is headers plus one
  slice copy. Wire shape in docs/openapi.yaml (`VersionResponse`).
- **Compatibility** — additive release; no consumer change required to bump.
  go.mod keeps the `go 1.27` floor (major.minor-only form), so consumers need
  Go 1.27+ toolchains.
- **Verification** — full gate sweep green at release (test, race, lint, vet,
  gosec, govulncheck, fuzz; re-verified 2026-10-08 on the release + master).
  A fresh-user simulation against the released tag (new module, module-proxy
  resolve, no replace directive) exercised the batteries, the boot-contract
  validation (`Start` rejects an unknown critical name), and the version
  endpoint end-to-end. Golden-wire lockstep (openapi-lockstep) green.
