00Summary

Yes — where go-etag is used, it is used superbly. All 10 production import sites use the modern server/client package paths (zero deprecated-root imports), memory bounds are configured wherever responses are wrapped, and go-github-kit's client transport is textbook RFC 9111 usage: credential-scoped keys, §4.3.4 freshening, and cache-marker headers. The version story is the only real gap: 68 of 77 referencing modules sit on the latest v0.3.1, while 9 lag on v0.1.0–v0.2.0 minimums — every one traceable to two library pins (stale httputil, unreleased go-github-kit), not to the applications themselves. go-health, the project that prompted this audit, does not use go-etag at all — correctly: caching health endpoints endangers the freshness that makes them worth polling.

The bottom line Zero misuse, 88% version currency, and one composition point (httputil's wrapper) where a single upgrade lifts 8 stale modules to v0.3.1 via MVS. The remaining work is release hygiene, not code.

◆What's already excellent

Evidence base: symbol-level audit of every production import site (etag.∗ / etagclient.∗ usage across cqrs-htmx ×4, DiscordSync ×2, go-github-kit, httputil, library-policy, nsfw-classifier).

+
Zero-config server middleware, everywhere it belongs etag.New ×16 and DefaultETagConfig ×17 wrap routes in cqrs-htmx (catalog, projection status, serve), DiscordSync, library-policy's httpapi, and nsfw-classifier — the RFC 7232 hard parts (304 bodies, weak comparison, HEAD) delegated, not hand-rolled.
+
Bounded memory is the norm, not the default MaxBodyBytes ×12, MaxEntries ×5, MaxBufferSize ×1 explicitly set — consumers did not leave the FIFO/cache-size safety valves at defaults.
+
go-github-kit: textbook client usage NewTransport with KeyFunc (credential-scoped cache keys), FreshenFields (RFC 9111 §4.3.4 header freshening), FromCacheHeader, and Stats() telemetry — conditional GET against the GitHub API is exactly what the client package was built for.
+
Strong validators respected SkipIfPresent ×2 lets handler-supplied entity-tags (e.g. database revisions) pass through untouched instead of being body-hashed over.
+
Zero deprecated-path debt All 16 imports use go-etag/server or go-etag/client; the deprecated root shim (slated for removal in v1.0.0) has no consumers.
+
go-health abstains, by design go-health's ROADMAP deferred an ETag rejection note "before someone asks"; this audit wrote it — docs/etag-rejection-design.md — citing go-etag's own v0.3.0 field report (a CDN serving a two-day-stale 200) as the reason health status-truth must never be cached.

01Findings

Ordered by impact. No misuses were found — every finding is a gap, not an error.

Important · 8 modules affected

Nine modules pinned to stale go-etag minimums via old httputil releases

go.mod of games/KeyCountdown (v0.1.0) · crush-daily, games/SEC, GmbH, GmbH/server, sales-landing-page/cloud-run, Standup-Killer, webphone (v0.2.0)

These modules never import go-etag directly; the requirement is // indirect, pulled by httputil. Their pins are httputil v0.11.0–v0.12.0, and httputil v0.12.0's released go.mod still requires go-etag v0.2.0 (verified: git show v0.12.0:go.mod). The fix is not touching these applications at all beyond one dependency bump: httputil v1.2.0 already requires go-etag v0.3.1 (verified: git show v1.2.0:go.mod), so MVS lifts the minimum the moment httputil is upgraded. 

# per affected module — one line, mechanical
go get github.com/larsartmann/httputil@v1.2.0 && go mod tidy
# go-etag minimum rises v0.1.0/v0.2.0 → v0.3.1 automatically
Recommendation Upgrade httputil to v1.2.0 in the 8 httputil-pulled modules (KeyCountdown double-benefits: httputil v0.11.0 → v1.2.0 also closes its v0.1.0 go-etag gap). Runtime risk is low for server-only consumers — v0.3.0's changes target the client package — but each module should still build and test after the bump.
Important · release hygiene

go-github-kit's go-etag v0.3.1 bump is unreleased, stranding one consumer

/home/lars/projects/go-github-kit · HEAD = v0.3.0-25 (25 unreleased commits) · released v0.3.0 requires go-etag v0.2.0

go-github-kit's working tree already requires go-etag v0.3.1, but the latest tag (v0.3.0) still requires v0.2.0 — the bump lives only in unreleased commits. standard-bug-tracking-schema (pins go-github-kit v0.2.0) therefore cannot reach go-etag v0.3.1 through any released path, unlike the httputil case.

Recommendation Tag go-github-kit v0.4.0 (the 25 queued commits include the bump), then go get github.com/LarsArtmann/go-github-kit@v0.4.0 in standard-bug-tracking-schema. Per the go-release discipline: verify build and the delivering layer before tagging.
Important · observability gap

Observability hooks are dark: no cache-hit visibility anywhere

OnETagGenerated ×0, OnBufferOverflow ×0, On304 ×1, Transport.Stats() ×1 across all import sites

go-etag ships exactly the hooks needed to answer "is conditional caching working?" — the CHANGELOG's ExampleNew_observabilityHooks derives a cache-hit ratio in six lines. No consumer wires them, so ETag effectiveness (hit ratios, degraded-to-streaming responses) is unmeasured across the entire ecosystem. The natural wiring point is httputil's wrapper: one composition, every wrapped app inherits the metrics.

Recommendation See the Target State section for the wrapper sketch. Start with On304 + OnETagGenerated (hit ratio) and OnBufferOverflow (alerts when bodies exceed MaxBufferSize and silently lose their ETag).
Nice to have · housekeeping

go-etag itself: 22 unreleased commits and one patch behind go-error-family

/home/lars/projects/go-etag · HEAD = v0.3.1-22 · go.mod pins go-error-family v0.10.0 (latest: v0.10.1)

The unreleased drift is real code, not docs: a typed error-code system (server/code.go +124 lines, wrapper.go migrated from errorfamily.Wrap* to code-receiver methods) plus its test suite. Until it is tagged, every future consumer gets the pre-refactor error surface. The go-error-family patch lag is trivial but free to close in the same release.

Recommendation Cut v0.3.2 (or v0.4.0 given the error-code surface change) from HEAD, bumping go-error-family to v0.10.1 in the same tag.
Nice to have · low relevance

not used anywhere: MatchesIfMatch, ParseETagList, Weak/Strong constants

If-Match optimistic concurrency (strong comparison) and manual entity-tag construction are unused across all consumers — but no current application implements conditional writes or revision checks, so this is a statement of relevance, not a gap. Listed for completeness; revisit if any service grows compare-and-swap update endpoints.

04Target State

After items 1–3: every referencing module resolves go-etag ≥ v0.3.1, and cache effectiveness is observable at the single point where responses are already wrapped: 

// httputil wrapper — wired once, inherited by every wrapped app
var etagHits, etagGenerated, etagOverflow atomic.Int64

cfg := etag.DefaultETagConfig()
cfg.On304            = func(etag.ETag) { etagHits.Add(1) }
cfg.OnETagGenerated = func(etag.ETag) { etagGenerated.Add(1) }
cfg.OnBufferOverflow = func(int) { etagOverflow.Add(1) }
// hit ratio = On304 / (On304 + OnETagGenerated), exported via /metrics
Why this state is better Version drift becomes structural (MVS via two libraries, not 77 manual pins), and the ecosystem's most-shipped middleware finally reports whether conditional caching is paying for itself — the question its own observability hooks were designed to answer.
